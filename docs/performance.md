# 实测性能与运行条件

本文说明用户实际会等待多久，以及当前为什么使用 CPU。手机翻译与朗读数据在 **2026-10-16** 使用已安装的 **Android 1.0.4 / versionCode 5** 补测；电脑记录和 GPU 对照按用户要求复用此前证据。只补充文档和实测记录，没有更换模型、降低精度、缩短正文或重新编译产品。

逐次数据见 [公开性能摘要 JSON](benchmarks/offline-performance-2026-10.json)。公开摘要从测试记录按字段白名单提取，不包含个人文章、学习档案、设备序列号、账号、密钥或个人备份内容。

## 翻译速度

### Android 1.0.4：实际安装包的 CPU 路线

在独立学习档案内，通过实际 WebView 调用 `ReadageTranslation.translate`。状态接口在首个请求前为 `uninitialized`，成功后实际后端均为 `cpu:libggml-cpu-android_armv8.2_2.so`。输入使用相同的公开测试短句与段落；两轮热运行分别穿插短句、段落，单个请求完整处理，无云端调用。

| 英译中样例 | 字符数 | 第一次测量 | 第二次测量 | 热运行中位数 |
| --- | ---: | ---: | ---: | ---: |
| 本进程首个短句请求 | 89 | **6.715 秒** | 不适用 | 不作为热运行样本 |
| 模型就绪后的短句 | 89 | 2.093 秒 | 1.775 秒 | **1.934 秒** |
| 模型就绪后的段落 | 451 | 7.400 秒 | 7.608 秒 | **7.504 秒** |

首个请求包含本进程首次模型准备，系统文件缓存仍可能保留，不能称为手机断电后的全冷启动。这里只有一个首次样本、每种热输入两个样本，尚无长时温控、后台负载或不同芯片的性能结论。

### 电脑本机：已有应用接口记录

2026-10-07 的本机 Hy-MT2 1.25bit 接口记录中，日语短句“図書館は午後六時に閉まります。”翻译为中文约 **2.5 秒**。1391 字符日语选区分为 587、595、209 字符三批，全部请求成功，合计约 **66 秒**返回 1308 字符中文译文。

这是既有单次应用流程记录，未保存可用于逐阶段统计的公开原始时序。本轮没有重测电脑，也不把该数值作为 Windows 0.1.2 安装版的新增端到端验收。原记录见 [本机翻译](local-translation.md)。

## 朗读等待、生成速度和连续播放

### Android 1.0.4：正式美音、1×、CPU 两线程

通过实际 APK 的 `ReadageBundledSpeech` 插件播放合成测试文本，记录首个原生输出、完整播放、正文范围和 `buffering` / `resume` 事件。84 字符短文分两段，451 字符段落分七段，所有输入范围均覆盖；只调用测试档案中的临时请求。

| 场景 | 首次原生输出 | 请求至播放结束 | 音频时长 | 运行中缺音频缓冲 |
| --- | ---: | ---: | ---: | --- |
| 84 字符新文本，首段缓存未命中 | **7.101 秒** | 11.729 秒 | 4.571 秒 | 本次 0 次 |
| 同一短文完整播放后重播，首段缓存命中 | **3.025 秒** | 7.659 秒 | 4.569 秒 | 本次 0 次 |
| 451 字符连续段落，首段缓存未命中 | **11.606 秒** | **40.565 秒** | **24.725 秒** | **2 次，合计 4.007 秒** |

三次请求的 `engineLoadMs` 均为 0，表明请求计时没有包含新的引擎加载。因此第一行应称“未命中首段缓存的新文本”，不能称“冷模型启动”。本轮没有测出完整应用启动、资源校验、模型冷加载到首次播放的总等待。

**当前这台手机的长段落仍会等待音频，不能写为连续朗读无停顿或音质验收通过。** 首段缓存只覆盖开头，重复同文时后文仍可能重新生成；多段开播还要准备约 4 秒音频内容，不能照搬旧包 24 毫秒重播记录。约 4 秒是音频长度，不是固定等待 4 秒。缺音频后当前策略准备约 3 秒内容再恢复；有限缓冲不能消除持续合成跟不上播放的问题。

2026-10-14 旧包的重启请求首次输出 6.963 秒、完整播放后重播 0.024 秒保留为历史结果，旧 APK SHA 为 `8ccef17d3aab17bcffc40bea458da58b0cd40ce1dde13faafe3fc4cb6e7d3090`。该结果不转作本次 1.0.4 的性能结论，详见 [旧包手机记录](android-install-test-2026-10-14.md)。

### Windows：已有 q8 / fp32 同机对照

2026-10-11 使用实际随包 Electron / ONNX 运行组件、Kokoro `af_heart`、1×、CPU 默认线程，各样例先预热再测两轮。下表为音频生成均值：

| 英语输入 | q8 | fp32 | fp32 对应音频时长 |
| --- | ---: | ---: | ---: |
| 5 字符短词 `Hello` | 1.294 秒 | **0.369 秒** | 1.325 秒 |
| 105 字符标准样例 | 6.665 秒 | **2.100 秒** | 6.750 秒 |
| 194 字符标准样例 | 12.938 秒 | **3.523 秒** | 13.275 秒 |

105 字符样例的 fp32 实时率约为 `2.100 / 6.750 = 0.31`；194 字符样例约为 `0.27`，即生成这些音频所用时间小于它们的播放时长。该实时率只说明这些直接合成样例，不保证所有语言、文章或电脑都能连续播放。

fp32 在后两个样例中约为 q8 的 **3.17 / 3.67 倍**生成速度，同时进程内存多约 **284 MiB**。fp32 载入约 1.576 秒、预热约 0.601 秒，分别记录，不混入上表。两种模型都已随 Windows 完整包提供；用户保存的合法设置继续保留。

### 本地浏览器：已有服务与缓存样例

2026-10-05，本机 Kokoro fp32、`af_heart`、1×：140 字符无音频缓存时，接口完整收到音频约 **2.346 秒**；相同音频命中服务端缓存后约 **7.3 毫秒**。142 字符原开头完整准备约 2.177 秒，按自然停顿分出的 51 字符首段约 0.814 秒具备音频，后文继续处理。

这些是预热后的单次接口测量，浏览器音频设备初始化及可听首音不在计时范围。不能把缓存返回的毫秒数用来描述首次合成速度。

## 可选播放语速与资源成本

共用朗读控件提供 **0.75×、0.9×、1×、1.1×、1.25×、1.5×** 六档，见 [`SpeechControls.tsx`](../src/components/SpeechControls.tsx)。语速改变实际播放节奏，音频生成能否跟上仍取决于模型、文本和设备；上面的语音实测均使用 1×，本轮没有重测其他语速或语言。

| 资源 / 成本 | 当前记录 |
| --- | --- |
| Windows Hy-MT2 1.25bit 文件 | 461,860,800 字节，约 440 MiB |
| Android Hy-MT2 Q4_K_M 文件 | 1,133,080,448 字节，约 1.06 GiB |
| Windows Kokoro fp32 / q8 文件 | 约 310 / 88 MiB；文件体积不等于模型运行的总内存 |
| 既有 Android 翻译优化 CPU 进程 RSS | 独立运行器峰值约 1389 MiB，2026-10-15；不是当前完整应用的峰值内存 |

首次部署资源、进程首次校验、模型加载、排队和后台负载都会影响等待。当前 APK 启动先准备正式资源，同一进程内后续请求复用已准备状态；没有将“每次翻译都重新读取全部模型资源”写成原因。

## 为什么当前手机使用 CPU

以下 **只复用 2026-10-15 的 Hy-MT2 翻译对照**，没有重新测试 GPU，也没有用本轮 WebView 耗时和旧独立 GPU 运行器计算倍率。正式 Q4_K_M 模型、完整测试输入及设备相同，每个配置 / 输入两个热样本；短句和段落分别为 41、104 个输入 token。

| 当时同条件配置 | 短句中位数 | 段落中位数 | 峰值进程 RSS |
| --- | ---: | ---: | ---: |
| 优化 CPU | **2.319 秒** | **9.246 秒** | **1389 MiB** |
| GPU，旧 NDK 编译器 | 23.761 秒 | 59.742 秒 | 2239 MiB |
| GPU，新编译器 / 整数点积 | **8.328 秒** | 未测 | 2246 MiB |
| GPU 输入 / CPU 生成，连续 KV 布局原型 | 6.782 秒 | 14.801 秒 | 3405 MiB |

原因有实际日志与分阶段数据支持：GPU 日志确认 33 / 33 层已经卸载，实验确实执行了 GPU 推理。旧 NDK 着色器编译器不支持所需整数点积，换用较新且固定版本的编译器后仍约 8.33 秒，约为同条件 CPU 短句耗时的 3.6 倍。GPU 输入处理较快，但本次逐 token 生成路线较慢，整体耗时和内存占用均未胜过优化 CPU。

GPU 输入 / CPU 生成原型也做了对照：短句 2.62 MB 的 KV 状态传递约 4.77–4.84 秒，段落 6.75 MB 约 7.14–7.31 秒，抵消了 GPU 输入处理的收益。该原型只保留实验结果，正式应用没有采用。完整配置、取消与回退的证据范围见 [此前 GPU 实测记录](android-gpu-2026-10-15.md)。

所以正式翻译继续使用已验证的 CPU 路线，实验 Vulkan 默认关闭。此决定针对这台 **Exynos 1080 / Mali-G78** 和当前模型 / 运行器，不推断 Adreno、其他骁龙或天玑设备的结果，也不承诺功耗优势。

**语音单独说明：** 正式 Android 朗读配置在 `ReadageBundledSpeechPlugin.java` 中明确使用 `provider="cpu"`、两线程。现有包没有经过验证并交付的 GPU 语音推理路线；本轮也未测试语音 GPU。不能用上述翻译 GPU 实验宣称 Kokoro 或 Supertonic 的 GPU 合成一定更慢。

## 资料保护与验收范围

更新前保存完整个人资料备份；第一次安装被用户误退出后，只补存三个变更文件再正常重试。覆盖更新使用已发布 APK，不卸载、不清数据。启动前核对手机实际安装哈希与 Release 一致，学习数据库、偏好及已有资料逐文件哈希保持一致。

CPU 测量在独立测试档案中进行，测试期间原档案的七张逻辑表及文章内容摘要保持一致，结束后恢复原档案与原路径。测试备份和设备原始报告只留在本机忽略目录，未进入 Git 或 Release。

本轮覆盖正式模型的原生返回、音频范围、首次输出、缓冲事件和播放完成。触屏按钮、朗读方框的实际移动、多语言 / 多语速、整本书持续播放及正式听感没有因此批量通过；对应 [D01、S01、S15、S20、S21 的限定记录](user-feature-acceptance.md#2026-10-16-android-cpu-性能实测)。
